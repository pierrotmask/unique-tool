# 利用者のデータを壊さない変更

「すでに使っている人のデータが壊れないように」は常に最優先にする。ストック（利用者が登録したもの）は変えない。提案内容は変わってよい。

## 1. 新しい設定・状態を足すとき
- 初期値は `DEFAULT_STATE()` に足す。読み込み時に `Object.assign(DEFAULT_STATE(), 保存データ)` で補われる
- 保存データの点検関数（`sanitizeState` など）で、**値の妥当性を必ず確かめる**
  - 範囲外の値、存在しない ID、型違い、配列でないもの、重複を直す
  - 例：`if(![1,2,3,4,5,6].includes(S.people)) S.people=2;`
- **「既存の利用者に一度だけ何かをする」目印は `DEFAULT_STATE` に入れない**
  - 入れると、既存の利用者にも初期値として目印が入ってしまい、その処理が一度も走らない（実際に起きた失敗）
  - 目印は点検関数の中で「なければ処理して立てる」形にする：`if(!S.flag){ S.flag=1; …一度だけの処理… }`
- 起動時に動く点検関数の中では、ファイルの後ろの方で定義した `const` を使わない
  - 使うと「Cannot access 'X' before initialization」で起動できなくなる
  - 必要なら、その場に値を直接書く（例：`['auto','side','soup','full'].includes(...)`）

## 2. マスターデータを変えるとき（食材・味付け・レシピなど）
- **ID は変えない・使い回さない**。表示名は変えてよい
- 廃止・統合するものは**内部データに残す**
  - 「提案には出さない」印を付けて、新しい提案から外す
  - 過去の献立・お気に入り・共有リンクの表示は壊さない。開いたら「○○に置き換えました」と案内し、移動先を示す
  - 種類別の件数表示や設定画面の一覧からは除く
- 追加するものは、既存との関係（似た使い方の既存項目／合わない組み合わせ）で、既存の組み合わせ規則につなぐ
  - 既存データの書き換えは最小限にする
- 保存データの点検では、存在しない ID を参照しているデータだけを取り除く（画面が壊れないように）

## 3. 共有リンク・コードの形式
- 番号の対応表（例：`SHARE_BASES` / `SHARE_PARTS`）は**末尾に足すだけ**にする。並べ替え・削除はしない（旧リンクの番号がずれる）
- 入りきらなくなったら新しい形式（先頭の文字を `A` から `B` にするなど）を足す
  - 読み込みは新旧両方に対応する
  - 書き出しは、旧形式で足りるときは旧形式を使う
- 新しい種類のデータ（例：献立の中の定番レシピ）は、旧形式の範囲外の番号で表す
  - 古いアプリは「読み込めない料理」として飛ばすので、エラーにならない
- 受け取り側は、知らないデータを `missing` として数えて飛ばし、全体は読み込む

## 4. 同じデータの写しが複数あるとき
- 例：作成中の献立と確定済みの写し
- 片方を変えたら、同じ ID の写しすべてに同期する。同期用の関数を1つ用意して使う
- 再確定などで写しを作り直すときは、引き継ぐべき状態を落とさない
  - 例：仕込み済み、購入時点のスナップショット、チェック状態

## 5. 取り消せるようにする
- データを変える操作には「取り消す」を付ける
- 変更前の状態を JSON で写しておき、戻すときはそれで戻す
- 複数の写しに同期した変更は、戻すときも同期する

## 6. 確認
- 変更前の形の保存データ（新しい項目なし・旧 ID 入り）を入れて開く。消えない・壊れない・新しい初期値が入ること
- 壊れた値（範囲外・存在しない ID・型違い・重複）を入れて開き、修復されること
- 共有リンクを旧形式・新形式の両方で往復させること
- 結果は `full-check` スキルの報告にまとめる
